═══════════════════════════════════════════════════════════════════════════════
PRODUCT INTENT
═══════════════════════════════════════════════════════════════════════════════

What this is
  A new setup script (full_stack/setup1.2.py) that produces the same kind of client artifacts as full_stack/setup.py — datafile.json, query_template_bank.csv, value_bank.csv, config.json — but with three upgrades: (1) richer business context (location/operating model), (2) a much larger query and value bank, and (3) tester questions ranked by search interest so the banks reflect how real people actually search.

Who it's for
  The same user who runs full_stack/setup.py: developer or analyst setting up a client for the full_stack pipeline (setup → collect → analysis). Used when they want location-aware, high-volume, trend-informed question banks instead of the small default banks from setup.py.

What problem it solves
  Default setup generates only a handful of templates and values; questions can feel generic or off from real search behavior. Setup1.2 fixes that by asking where the business operates, generating many diverse tester questions, ranking them by trends, and using the top 25 to shape a large template/value bank so the expanded questions look like what people actually ask.

Outcome
  After running setup1.2: client folder has datafile.json (with operating_model + operating_region), 50 unique tester questions ranked by trends, top 25 driving bank generation, and large query_template_bank.csv + value_bank.csv + config.json; build_queries_from_matrix produces no unfilled placeholders and stays under a safety cap; console prints next step (run collect.py).


═══════════════════════════════════════════════════════════════════════════════
HOW IT WORKS
═══════════════════════════════════════════════════════════════════════════════

High-level flow
  1. User runs setup1.2 with a slug (or is prompted). Script normalizes slug, checks idempotency (refuse if banks/config already exist), creates client folder.
  2. Interactive chat collects business context (same as setup.py) plus operating_model (physical / online / both) and operating_region (city/region/country or "online/anywhere"). Results written to datafile.json.
  3. Location-aware rules are encoded so later generation uses or avoids {city}, {landmark}, {neighborhood}, {location} depending on operating model/region.
  4. Generate ~50 unique tester questions (intent buckets + format diversity + dedupe). Rank by Google Trends (or chosen trends source), keep top 25.
  5. Generate a much larger template bank and value bank, shaped by the top 25; validate with build_queries_from_matrix (no unfilled placeholders; enforce max-expansion cap).
  6. Write query_template_bank.csv, value_bank.csv, config.json; print "review banks then run collect" and the collect.py command.

Architecture (components + responsibilities)
  - setup1.2.py: Single entrypoint; orchestrates collect → tester questions → trends → bank generation → write. Reuses full_stack.lib, full_stack.schema; does not modify setup.py.
  - datafile.json: Extended schema (existing keys + operating_model, operating_region). Input to all generation prompts.
  - Tester-question pipeline: LLM candidate generation with buckets/quotas → dedupe (embedding similarity per BUILD-TIME DEFAULTS) → trend scoring → top 25.
  - Bank generation: LLM prompts that receive top 25 as examples/guidance; output rows validated and capped.
  - External: OpenAI (generation + embeddings). Google Trends via pytrends (ranking). OPENAI_API_KEY required in .env at repo root (script exits with message if missing).

Key data (inputs/outputs)
  - Inputs:
    - Slug (CLI or prompt), .env (OPENAI_API_KEY). Optional: client_folder/addable_allowlist or blocklist not used by setup1.2.
  - Outputs:
    - client_folder/datafile.json, client_folder/query_template_bank.csv, client_folder/value_bank.csv, client_folder/config.json. Optional: intermediate top25 or tester_questions JSON for debugging.

Error handling + retries
  - Missing OPENAI_API_KEY: exit with clear message (no crash).
  - Idempotency: if query_template_bank.csv or config.json already exists, print "Already set up for '<slug>'. Delete bank CSVs and config.json to re-run setup." and exit (see Step 0.1.1).
  - build_queries_from_matrix: if placeholders remain or count exceeds cap, treat as validation failure (fix or truncate before write).
  - Trends API rate limits: document in CONSIDERATIONS; optional backoff or "trends-only" re-run without regenerating banks.

CONSIDERATIONS / GOTCHAS
═══════════════════════════════════════════════════════════════════════════════

Constraints
  - Google Trends (or pytrends) rate limits and geo/time-range limits; may need US vs client geography and 12-month window.
  - OpenAI token usage scales with larger banks and 50+ tester prompts; keep generation prompts bounded.
  - Full template × value matrix can explode; MUST enforce a max-expansion cap (single source of truth in code).

Assumptions
  - datafile.json from setup1.2 is backward-compatible for collect/analysis (existing keys unchanged; new keys additive).
  - Top 25 "shape" bank generation by inclusion in prompts as examples (not by changing schema).
  - Schema: TEMPLATE_HEADERS and VALUE_HEADERS from full_stack/schema.py stay as-is unless a separate decision adds columns.

Risks + mitigations
  - Risk: Trends API unavailable or blocked. Mitigation: document manual export option; or make "trends step" skippable with a flag and use unranked 50.
  - Risk: Dedupe too aggressive or too loose. Mitigation: pick one method (embedding threshold or LLM grouping), document threshold in SPECIFICATIONS.

Non-obvious pitfalls
  - Physical vs online: if "online only," avoid generating "X near {city}" as primary; if physical, require at least one location placeholder. Encode this in prompt rules so the model doesn't guess.
  - Progress bar: use same style as setup.py (20-segment _bar(current, total)). Call _bar(1,5) after collect context, _bar(2,5) after 50 tester questions, _bar(3,5) after top 25 selected, _bar(4,5) after bank generation + validation, _bar(5,5) after writing CSVs and config. So phases are: 1=collect, 2=tester questions, 3=trends, 4=banks, 5=write.
