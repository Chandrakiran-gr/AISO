────────────────────────────────────────────────────────────────────────────────
PROCESS: Make `collect.py` faster without changing its data contract
────────────────────────────────────────────────────────────────────────────────

Input: `query_template_bank.csv` and `value_bank.csv` in a client folder.

Core work: build the full `questions` list (same as collect.py) then run `webish(query)` for each question.

Constraint: output must remain compatible with the existing pipeline:
  - same CSV columns: `question,response,error`
  - same output filename rule (“next N” based on existing `{slug}_aisodata*.csv`)
  - same row order as `collect.py`’s question list

Strategy:
  1. Remove avoidable overhead inside `webish/api_query.py` (cache the system prompt loaded from disk).
  2. Run web requests in parallel with a fixed cap on concurrency (to reduce `429` retry “thrash”).
  3. Preserve exact ordering by attaching question indices and sorting within each batch before writing (ordering becomes deterministic even if workers finish out of order).
  4. Write CSV incrementally (batch-by-batch) to keep memory stable.


═══════════════════════════════════════════════════════════════════════════════
PRODUCT INTENT
═══════════════════════════════════════════════════════════════════════════════

What this is
  A faster drop-in runner: `python full_stack/collect1.2.py <slug_or_path>` that produces the same kind of output CSV as `full_stack/collect.py`, but with much lower runtime on large question sets.

Who it's for
  The developer running the full_stack pipeline (setup → collect → analysis1 → downstream scripts) and needing large-load speedups.

What problem it solves
  `collect.py` runs `webish(query, mode="api")` sequentially for every question, so large loads take a long time even though the work is network I/O bound.

Outcome
  A significantly faster collection run while preserving the CSV “contract” (columns, filename rule, row order, error capture behavior).


═══════════════════════════════════════════════════════════════════════════════
HOW IT WORKS
═══════════════════════════════════════════════════════════════════════════════

High-level flow
  1. Resolve `slug` and `client_folder` (same as collect.py).
  2. Load `query_template_bank.csv` and `value_bank.csv`.
  3. Build `questions` with `build_queries_from_matrix(template_rows, value_rows)`.
  4. Validate that `questions` are non-empty and fully filled (no `{...}` placeholders remain).
  5. Split `questions` into batches (so we can write incrementally).
  6. For each batch:
     - run that batch's questions in its worker (sequentially inside the worker, but multiple workers run in parallel)
     - enforce a fixed global concurrency cap via `MAX_IN_FLIGHT` (= number of concurrent worker-batches)
     - catch exceptions per question and convert them to `error=str(e)` with `response=""`
     - sort results by original question index
     - append rows to the output CSV
  7. Print the same success/failure summary.

Data flow
  - Input: two CSV banks per client.
  - In memory: questions list + current batch results.
  - Output: `{slug}_aisodata{N}.csv` with header `question,response,error`.

Integrations
  - Reuses `full_stack/collect.py`’s `resolve_client_folder()` + `normalize_slug()` logic.
  - Reuses `full_stack/lib.py`’s `read_csv_to_rows()`, `build_queries_from_matrix()`, `call_webish()`.
  - Reuses `webish/webish.py`’s formatting behavior via `call_webish()` (so response formatting stays identical).

Edge cases
  - Missing CSV banks: exit with clear message (same as collect.py).
  - Invalid/empty question list: exit (same checks as collect.py).
  - Individual question failures: write error into that row; continue the run.

CONSIDERATIONS / GOTCHAS
═══════════════════════════════════════════════════════════════════════════════

1) “Exact same results” vs nondeterminism
  - Even with the same parameters, LLM web-search outputs can vary run-to-run.
  - The plan guarantees:
    - exact same mapping question[i] → response/error row[i]
    - exact same CSV order
    - same formatting behavior
  - It does not guarantee byte-identical response text across independent runs unless you add a caching layer for responses.

2) 429 rate limiting
  - Too much concurrency can trigger many 429s and make performance worse.
  - The runner must cap in-flight requests and retry behavior must remain centralized in `webish/api_query.py`.

3) Memory pressure
  - Holding all responses for huge loads can bloat memory.
  - The runner should write batch-by-batch to avoid accumulating all rows in memory.


═══════════════════════════════════════════════════════════════════════════════════════
DECISIONS / GATHERED INFO
═══════════════════════════════════════════════════════════════════════════════

Gathered from code inspection
  - `full_stack/collect.py` is a simple for-loop; runtime is dominated by `call_webish(question)` per question.
  - `webish/api_query.py` loads the system prompt from disk per request via `_load_browser_like_prompt()`.
  - `webish/api_query.py` catches `RateLimitError` and sleeps with exponential backoff, so concurrency affects runtime dramatically.

Chosen approach
  - Keep request semantics: still call `call_webish(question)` once per question.
  - Improve speed by:
    - caching the system prompt in `webish/api_query.py`
    - running worker-batches in parallel with a fixed global cap (`MAX_IN_FLIGHT`)
    - preserving output order via question indices
    - incremental CSV writing
