────────────────────────────────────────────────────────────────────────────────
PROCESS: How to identify "addable" sources from the business-column data
────────────────────────────────────────────────────────────────────────────────

Input: The business columns in the enriched aiso CSV. Each cell contains markdown links [text](url) — the sources ChatGPT cited for that business for that question.

Step 1: Extract all unique domains from the cited links.
  • Parse each markdown link to get the URL.
  • Extract the domain (e.g. venturacountycoast.com, islandkayaking.com).
  • Dedupe across all rows and all business columns.

Step 2: Classify each domain as "addable" or "not addable".
  • Core rule: Addable = a site where a business can actually be added (directory, tourism bureau, visitor bureau, chamber, listing site). Not addable = anywhere a business cannot submit or request inclusion.
  • Competitor sites: Competitor dot-coms don't match addable patterns (chambers, tourism, etc.) so they're naturally excluded. No extra competitor-domain filter needed.
  • .gov: Include .gov sites that accept listings (city/county chambers, visitor bureaus). Exclude .gov that don't (nps.gov, editorial). Don't blanket-exclude *.gov.
  Heuristics:
    — Addable: visit*.com, *tourism*.org, *chamber*, *visitor*, travel aggregators, activity directories, municipal/parks (cms.*, revize*), paddle/kayak directories, city/county .gov that list businesses.
    — Not addable: en.wikipedia.org, nps.gov, news sites (latimes, etc.), editorial .gov. No blanket *.gov exclusion.

Step 3: For each addable domain, verify before keeping it:
  (a) A business like the one in the slug (use slug's datafile: industry, products_services, geography, etc.) can actually be added to that site — e.g. the site accepts that type of listing, serves that geography, or has a submission process. (Phase 1: geography-only via relevance filter. Full industry/products_services verification deferred to Phase 2.)
  (b) CRITICAL: The business in the slug is NOT already listed on that addable website — if the focal business is already there, do not include it in the output.
  Only domains that pass both checks remain in the addable list.

Step 4: Pick the best URL per addable domain (prefer submission/add pages over deep links).
Step 5: Optional relevance filter using datafile (exclude domains clearly for a different region).
Step 6: Compile into list and write to CSV:
  • Filename: {slug}_aisodata{N}_new_addable.csv
  • Output: Single column (url), one website per row. Each URL = best URL for that domain (submission page or base URL).

PRODUCT INTENT
═══════════════════════════════════════════════════════════════════════════════

What this is
  A script that outputs {slug}_aisodata{N}_new_addable.csv — a list of addable websites where the focal business could get listed but is not already.

Who it's for
  The developer or analyst running the full_stack pipeline after analysis1. Same user who runs setup, collect, and analysis1. Used when generating outbound-listing recommendations for a client.

What problem it solves
  Identifies actionable outbound-listing opportunities: sites ChatGPT cited for competitors (or general context) that the business could realistically submit to.

Outcome
  A nice list of websites to add the business to.

HOW IT WORKS
═══════════════════════════════════════════════════════════════════════════════

High-level flow
  1. User runs analysis2 with a slug (or client folder path). Script resolves to client folder and slug (same pattern as collect and analysis1).
  2. Script finds the latest enriched {slug}_aisodata{N}.csv (one that has analysis1 columns: focal, competitors, Unassigned). If none exists, exit with clear message.
  3. Extract all unique domains from every business-column cell (parse [text](url), get domain, dedupe). Exclude domains that appear only in the focal business column — those sources cited the focal business, so the focal is likely already listed there. Focus on domains from competitor columns and Unassigned (potential new-addable opportunities).
  4. Classify each remaining domain as "addable" or "not addable" using heuristics (directories, tourism bureaus, chambers, visitor info → addable; competitors, Wikipedia, news, government editorial → not addable).
  5. Filter: blocklist (exclude), allowlist (include), relevance (datafile geography — exclude wrong-region domains).
  6. Pick best URL per domain: prefer paths with add|list|submit|directory|businesses|list-your; else base URL.
  7. Write {slug}_aisodata{N}_new_addable.csv: single column (url), one website per row. Each URL = best URL for that domain.

Data flow
  • Input: client folder (from slug/path), latest enriched aiso CSV (with Unassigned in header).
  • In memory: rows, business column names, focal column name; extracted domains with source (which column they came from); classified addable/not; filtered list.
  • Output: {slug}_aisodata{N}_new_addable.csv in the same client folder; UTF-8.

Integrations
  • Reuses slug/client-folder resolution (same as collect and analysis1 — resolve_client_folder, normalize_slug).
  • Reads enriched CSV only; no external APIs required for basic flow. Optional: lightweight web check (e.g. requests) to verify focal not listed — can be deferred to a later step.
  • Reads datafile.json for business context (industry, products_services, geography) when doing addable verification.

Edge cases
  • No enriched CSV: exit with "No enriched aiso data found. Run analysis1 first."
  • Empty business columns / no links: output CSV has header but zero addable domains.
  • All domains in focal column: no "new addable" opportunities; output empty list.
  • Malformed markdown links: skip or best-effort parse; do not crash.
  • Empty domain from URL (e.g. relative URL, mailto:): skip; do not add to domain_to_info.
  • CSV with BOM: If CSV was saved with UTF-8 BOM, open with encoding="utf-8-sig" to strip BOM; or use utf-8 and accept first column name with BOM — analysis1 writes without BOM.
  • No backup: Re-run overwrites {slug}_aisodata{N}_new_addable.csv; no backup of previous run.

CONSIDERATIONS / GOTCHAS
═══════════════════════════════════════════════════════════════════════════════

  • Focal-column exclusion: Domains that appear only in the focal business column are treated as "focal already listed there" — exclude from output. This is heuristic; some focal citations might be from the focal's own site or tangential. Conservative approach: exclude focal-column domains.
  • Competitor-column focus: Domains from competitor columns are the primary source of "new addable" opportunities. Competitor dot-coms don't match addable patterns (chambers, tourism, etc.) so they're naturally filtered out.
  • Heuristic brittleness: Addable/not-addable rules are pattern-based. Optional allowlist/blocklist files in client folder override: addable_allowlist.txt (one domain per line — always include) and addable_blocklist.txt (always exclude). Use for edge cases.
  • "Not already listed" verification: Full web check (visit each site, search for focal name) is expensive and brittle. Phase 1: heuristic only (exclude focal-column domains). Phase 2 (future): optional lightweight check.
  • Empty output: If all cited domains are in focal column or all are "not addable," output will be empty. That's valid — no new opportunities found.
  • Focal column: analysis1 always produces focal + competitors + Unassigned; focal is first. If only Unassigned existed, focal_col would be Unassigned — treat as edge case (analysis1 does not produce that).
  • Link format: Cells may have multiple links (newline-separated). Parse each [text](url) in each cell.
