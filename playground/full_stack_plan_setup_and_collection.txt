AI EXECUTION NOTES (trip wires to avoid)
═══════════════════════════════════════════════════════════════════════════════

These notes help an AI executor avoid common failures. Do not skip them.

  • Run from repo root and Python path: Commands are run from Integrated_ai (repo root). So that `from full_stack.lib import ...` and webish import work, either: (a) set PYTHONPATH to repo root, or (b) at the top of setup.py and collect.py add: import sys; from pathlib import Path; root = Path(__file__).resolve().parent.parent; sys.path.insert(0, str(root)). Pin one approach and document it in .env.example or README. Do not assume "run from repo root" alone makes full_stack importable.
  • No browser verification: Use programmatic verification only (e.g. assert CSV files exist, row counts, build_queries_from_matrix returns questions). Do not leave verification steps that require a human to open a URL.
  • Banks are CSV files: Query template bank and value bank live in each business folder as query_template_bank.csv and value_bank.csv. Setup writes them; Collect reads them. No Google Sheets. Lib must provide read_csv_to_rows(path) or equivalent (return list of dicts) and build_queries_from_matrix(template_rows, value_rows).
  • Pin names to avoid drift: Use one shared module (lib.py) for CSV read, query build, and webish. Name the webish wrapper call_webish. Use datafile.json (JSON only). .env.example: OPENAI_API_KEY= (no Google var required for setup/collect).
  • Webish import: Use `from webish.webish import webish` (or path per repo layout). The wrapper in full_stack.lib should call webish(query, mode="api") and return the string. Handle ImportError if run from different working directory (see path note above).
  • Interactive chat (1.2.1): To verify without a human, run with pre-filled stdin or unit-test the chat loop with mocked input. Do not mark 1.2.1 complete on "code exists"; confirm it runs and collects the required fields.
  • Collect input: Collect accepts business folder path or slug. If path: use it as the client folder. If slug: resolve to Integrated_ai/<slug>/. Require query_template_bank.csv and value_bank.csv in that folder; fail with clear message if missing.
  • Next N and client path: Step 2.5.1 uses the client folder path (from 2.1). List <slug>_aisodata*.csv in that directory to determine next N. Pattern uses the actual slug (e.g. acme_aisodata*.csv for slug acme).
  • Fail clearly: Whenever the plan says "exit with clear message," exit with non-zero and a single, copy-pastable message (e.g. "Business folder not found: ..." or "Missing query_template_bank.csv in ..."). Avoid traceback-only exits.
  • LLM JSON parsing (1.4.2, 1.4.3): The model may return JSON wrapped in markdown code fences (e.g. ```json ... ```). Before calling json.loads, strip those fences; then parse. If you do not strip, parsing will fail.
  • Credentials: Use only OPENAI_API_KEY from env for setup/collect. Do not copy hardcoded API keys from SBACO.
  • Paths: read_csv_to_rows and file paths (e.g. client_folder / "query_template_bank.csv") should accept str or pathlib.Path; normalize so they work when run from repo root.
  • Schema (0.2): Derive template/value structure from SBACO aoi_benchmark_0.py (build_queries_from_matrix, template rows with {placeholder}, value rows with matching keys). Template CSV may be single column (e.g. "query") or multi-column; value columns = placeholder names. Document clearly so 1.4 and 2.2 stay consistent.

PRODUCT INTENT
═══════════════════════════════════════════════════════════════════════════════

What this is: A reusable toolkit (one folder of scripts) to set up and run AISO collection for any new client. Same setup + collect flow for every client; no client-specific code.

Who it's for: You / Integrated AI. You run the same tools each time you onboard a new client.

What problem it solves: Today, setup and collection are manual or one-off. With this plan: run setup for a new client → run collect when you want fresh data → get versioned answer data. The toolkit is reusable; you are not building one flow for one specific business.

Why it matters: One set of tools, many clients. Query and value banks stay fixed per client so AISO scores are comparable across runs; versioned CSVs give a clear history of what AI returned when.

Not in scope: Defining or hardcoding one specific business. This plan builds the reusable setup and collection only.

═══════════════════════════════════════════════════════════════════════════════
HOW IT WORKS
═══════════════════════════════════════════════════════════════════════════════

High-level flow (same for every client):

  1. Setup (once per new client)
     Input: Run setup (e.g. python full_stack/setup.py). Script gets slug (CLI or prompt), creates the business folder, then runs a required short chat to collect client context (e.g. industry, products, geography) into a datafile — setup does not proceed past the chat until the datafile is written; same mechanism for any client; no logic tied to one business.
     Process: Get slug (CLI or prompt). Create folder Integrated_ai/<slug>/. Say e.g. "Please do this quick chat" and run the chat; when complete, write datafile. Generate query template bank and value bank from datafile via AI + guidance; write them as CSV files in that business folder (query_template_bank.csv, value_bank.csv). No Google Sheets. Optionally write config (slug, display_name) in that folder. Recommend human review; banks are not edited after setup.
     Output: Business folder with datafile.json, query_template_bank.csv, value_bank.csv, and optional config.json.

  2. Collect (run whenever you want fresh data for that client)
     Input: You say what to collect for; you give the directory to the business folder (the folder created by setup) — e.g. path or slug so the script resolves Integrated_ai/<slug>/.
     Process: Read template and value banks from that business folder (the CSV files) → compile full question list (template × value rows, placeholders filled). Pass each question through webish(question, mode="api"); collect response (and optionally sources). Write results to a new CSV: slug_aisodataN.csv in that same business folder (N = next available index).
     Output: New CSV file in the business folder; previous CSVs left untouched.

Key point: The toolkit is client-agnostic. You reuse it for any new client; client-specific data (datafile, query template bank CSV, value bank CSV, output CSVs) lives in that client's folder. Banks are stored in CSV files in each business folder, not in Google Sheets.

Key integrations: webish (existing), filesystem (per-client folders + CSV banks + versioned output CSVs). No Google Sheets for banks.

HOW TO USE / RUN
═══════════════════════════════════════════════════════════════════════════════

  • Env: OPENAI_API_KEY (for webish and setup AI) — same as SBACO/webish (.env in webish or repo root). No Google Sheets; no service account required for setup/collect.
  • Commands: From Integrated_ai (repo root), python full_stack/setup.py (new client: asks questions, creates business folder and CSV banks), python full_stack/collect.py (then provide business folder path or slug to collect for).

Validation: before writing, ensure required keys (industry, products_services, geography) are non-empty; if missing, loop back in chat or exit with a clear message rather than writing an invalid file. Do not add YAML unless the plan is updated; stick to JSON so all steps (e.g. 1.4.1) have a single, unambiguous format.
